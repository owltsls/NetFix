# 方案比选记录 — NetFix 网络异常修复工具

> 生成日期：2026-11-23
> 依据：`references/risk-and-option-review.md` 第 4 节加权评分法
> 需求特性：Windows 系统级网络配置读写（注册表 / netsh / 环境变量 / hosts / WMI），产出 `.exe`，完全离线

---

## 1. 候选方案

| 方案 | 名称 | 技术栈 | 核心思路 |
| --- | --- | --- | --- |
| A | C#/.NET 原生 | .NET 8 LTS + WinForms + 自包含发布 | 用 .NET 原生调用注册表、System.Net、Process 执行 netsh，单文件 exe |

## 4. 推荐结论

**推荐方案 A（C#/.NET 原生，加权 4.00）**

理由：
1. 系统级网络能力（注册表代理项、netsh、WinHTTP、环境变量）用 .NET 原生 API 调用最直接，无需跨语言桥接，稳定性最高；
2. 自包含单文件 exe 启动快、体积可控，且不像 PyInstaller 那样容易被安全软件误报——对一个"网络修复工具"而言，被误报为病毒是致命的信任问题；
3. 许可生态干净（MIT / .NET 许可可商用），无传染性许可风险。

**MVP 范围建议**：仅 Must 级功能——8+ 通道一键体检、修复前快照、一键恢复初始状态、一键回滚、UAC 权限处理。Should 级（分项修复、报告导出、知识说明、代理软件检测）视排期纳入。

**否决理由**：
- **方案 B（Python+PyInstaller）**：PyInstaller 产物被 Defender/360 误报概率高，对网络修复类工具是致命信任问题；冷启动 3–8 秒、体积 100MB+；GPL+exception 许可需审查。开发快不足以抵消上述三项，否决。
- **方案 C（Go+Wails / Rust+Tauri）**：需求仅 Windows 单端系统级修复，跨平台框架是过度设计；需额外引入 Go/Rust + 前端工具链，环境匹配度最差，且交付体积不小。否决。

**待用户拍板的分歧点**（Round 1）：
1. 修复边界 Q-04（hosts 自定义条目、环境变量代理是否纳入）
2. 开发机 Q-02/Q-03（Windows 直开 vs Mac+CI，是否已有 .NET SDK）
3. 签名 Q-06（未签名接受度 vs 证书投入）
